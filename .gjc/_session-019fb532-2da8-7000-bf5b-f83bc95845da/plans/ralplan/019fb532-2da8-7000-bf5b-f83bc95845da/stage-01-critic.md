## Verdict
**ITERATE**

## Claim Checks
The plan’s repository diagnosis is materially accurate. `scenes/main.tscn` is a scripted root; UI is programmatic GDScript. `project.godot` contains keyboard/mouse actions and no controller bindings or remapping. `scripts/player/player.gd` grants club, 10 wood, 6 stone, and five raspberries; `scripts/ui/hud.gd` fades messages after 4.0 seconds. `scripts/core/recipe_db.gd` exposes hammer, torch, club, and stone axe as handcraft recipes. `scripts/core/game_state.gd` has no objective/tutorial state, and `scripts/core/save_system.gd` is version 1. `scripts/ui/ui_theme.gd` makes helper-created buttons `FOCUS_NONE`. `scripts/ui/map_ui.gd` is fixed at 880x860 and has no zoom/pan/pin interaction. `scripts/building/build_system.gd` uses boolean `_valid`, red/green ghost materials, generic rejection, and a no-op `_tint_support`; `scripts/entities/enemy.gd` uses a fixed 0.42-second telegraph. `scripts/world/spawn_manager.gd` exposes no persistent raid state and starts 6+tier*2 enemies after a generic message. `scripts/dev/screenshot_director.gd` uses staged grants, so separating marketing and acceptance profiles is justified.

The chosen vertical-slice option follows the stated drivers better than a visual-only reskin or broad rebalance. The sequencing also reflects real dependencies: inventory mutations are currently split between `Inventory` and direct UI slot writes; build preview and placement share only a local boolean; modal input/focus is centralized in `UIRoot`; and localization embeds `[E]` in both runestone strings. The proposed source-of-truth and UI boundaries are directionally sound.

Representative implementation simulation exposed one critical thin area. Current client building consumes materials in `BuildSystem.try_place()`, sends an uncorrelated request, and reports success immediately, while host `Net._request_place()` calls `place_remote()` without validating range, materials, station, overlap, ownership, or the requesting peer. The plan requires host/client validity agreement and visible pending/rejected state, but `ActionResult {ok, reason, cost, context}` alone does not specify the network transaction needed to achieve it. The role roster also does not assign `scripts/building/build_system.gd`, `scripts/building/build_piece.gd`, or `scripts/core/net.gd` ownership clearly.

A second simulation—settings plus legacy loading—also remains undecided. Phase 0 says to decide the settings persistence boundary, while file-level changes suggest `save_system.gd` may serialize settings. The acceptance criteria require locale, UI scale, audio, sensitivity, inversion, and reduced shake to persist across restart. Executors still need an explicit decision on profile-global `user://` configuration versus per-world save data, defaults, atomic writes, corrupt-file behavior, and which fields may be added while keeping version-1 saves readable.

A third simulation—playtest and visual release gating—finds strong matrices but insufficient scoring definitions. “Understand the next progression goal,” “median idle/confused interval,” “prepared early encounter,” “chosen Meadows enemy,” “approved archetype value,” and “correctly identify why 9/10 sampled actions” are not operationalized. The 65–85% combat band has no sample size or exact fixture. The 100 ms feedback criterion has no measurement start/end or instrumentation method. Safe margins, allowable clipping/overlap tolerance, screenshot combinations, and sign-off evidence are not fully specified. Reviewers therefore cannot objectively reproduce every gate yet.

## Missing Evidence
- Definitely missing: a concrete multiplayer action transaction contract for build placement and other authoritative actions, including request identity, pending state, host validation, peer/player inventory ownership, commit/reject response, resource consumption point, prediction/rollback policy, duplicate/replay handling, and disconnect/timeout behavior.
- Definitely missing: unambiguous role ownership and integration responsibility for `build_system.gd`, `build_piece.gd`, `net.gd`, atomic inventory/container actions, cross-cutting `ActionResult` definitions, and final host/client test fixtures.
- Definitely missing: the settings storage decision and migration/corruption policy. “Decide in Phase 0” does not let Phase 1 executors implement or reviewers verify persistence without another specification artifact and approval gate.
- Definitely missing: operational definitions and exact fixtures for the quantitative playtest gates. The target enemy/loadout/seed/location/time/weather, cohort eligibility, sample sizes, scoring questions, intervention/failure rules, idle/confusion coding, and aggregation method are unspecified.
- Definitely missing: a reproducible procedure for the 100 ms latency criterion and performance gate, including timestamp endpoints, hardware/build mode, run count, percentile, and frame-time budget during combat/raid.
- Thin area needing expansion: responsive visual acceptance needs numeric safe-area tokens, text overflow policy, modal maximum dimensions/scroll behavior, exact required screenshot manifest versus optional combinations, contrast measurement procedure, and pass/fail/sign-off record.
- Thin area needing expansion: controller feasibility has no pass criterion; either define prototype coverage and exit criteria or mark controller excluded for this release plan now.
- Thin area needing expansion: Phase 0 deliverables have no named artifact formats or completion checks for baseline observations, contracts, wireframes, and approval receipts.

## Approval Boundary
Phase 0 read-only baseline capture, repository-native measurement setup, wireframe drafting, and contract design may proceed. No Phase 1–4 implementation should be treated as approved until the authoritative transaction model, persistence boundary, ownership map, and objective verification protocols are added and accepted. The vertical-slice direction, non-goals, preservation constraints, screenshot-profile separation, and broad phase ordering are approved in principle; exact balance changes, controller support, save-version changes, dependencies, screenshot replacement, and multiplayer-authority changes remain behind the plan’s stated maintainer/architecture gates.

## Summary
- Clarity: Strong at product intent, affected surfaces, and phase ordering; thin at cross-process contracts and measurable gate procedures.
- Verifiability: Broad test/screenshot coverage is present, but several headline thresholds lack exact fixtures, definitions, sample sizes, or measurement methods.
- Completeness: Comprehensive feature inventory and risk coverage; missing transaction semantics, settings persistence design, and ownership for load-bearing cross-cutting files.
- Big Picture: The focused vertical slice is appropriate and avoids content expansion, but Phase 4 propagation must remain conditional on early gates to control scope.
- Principle/Option Consistency: Strong. Real-loop onboarding, progressive disclosure, shared grammar, and evidence-based tuning consistently support Option A.
- Alternatives Depth: Adequate; the three options have meaningful tradeoffs and a defensible choice.
- Risk/Verification Rigor: Strong pre-mortem and matrices, but not yet executable as an objective release protocol in the missing areas above.

## Required Changes
1. Add the concrete authoritative action protocol. For build placement, specify request/response schemas and reason enum/precedence; request correlation and idempotency; host checks for peer ownership, range, selected piece, materials, station, terrain/water/overlap/support and limits; when resources are consumed; how local pending ghosts and rejection recovery behave; and timeout/disconnect/replay handling. Apply the same explicit pattern where inventory, tomb, raid, or combat actions cross authority boundaries.
2. Add a responsibility matrix naming one owner and one integration reviewer for every cross-cutting contract and affected file, especially `build_system.gd`, `build_piece.gd`, `net.gd`, `inventory.gd`, container/tomb flows, save/settings, and objective events. State which contract artifacts must land before parallel implementation branches begin.
3. Resolve settings persistence in the plan: use a profile-global settings file or per-world fields explicitly; enumerate each setting/default; define legacy and corrupt-file behavior, atomic write/backup policy, live-apply versus restart behavior, and tests. Clarify whether `SaveSystem.VERSION` remains 1 with additive defaults or is raised behind maintainer approval.
4. Turn Phase 0 into an objective gate with named artifacts and acceptance checks: baseline manifest/log, event/result schema with complete enums and precedence, objective-state table, settings decision record, annotated responsive wireframes, owner approvals, and a criterion that Phases 1–3 cannot start against provisional contracts.
5. Specify playtest fixtures and rubrics. Name the Meadows enemy and exact starter loadout, seed/location/conditions, cohort inclusion criteria, minimum N per quantitative rate, handling of disconnects/interventions, the questions and scoring rule for “understands” and “attributable,” the definition/coding of idle-confused intervals, and the exact ten action cases used by the 9/10 gate.
6. Specify instrumented performance verification: input event timestamp to first animation/audio/UI response, local versus network endpoints, release/debug build, reference hardware, warm-up, sample count, percentile threshold, and combat/raid frame-time budget.
7. Make responsive/screenshot acceptance reproducible: define numeric safe margins, overflow/wrapping/scroll rules, required versus optional matrix combinations, automated assertions where possible, contrast tooling/procedure, image manifest schema, baseline comparison retention, and named visual/accessibility sign-off evidence.
8. Define controller prototype pass/fail criteria or explicitly exclude controller bindings and release UI from this iteration; do not leave support status to an unspecified later judgment.
