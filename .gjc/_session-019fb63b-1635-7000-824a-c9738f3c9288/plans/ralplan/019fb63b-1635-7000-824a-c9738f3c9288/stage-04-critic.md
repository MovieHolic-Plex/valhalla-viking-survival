## Verdict
**ITERATE**

## Claim Checks
- The pass resolves pass-3's three protocol blockers coherently by removing remote build support from RT1 rather than claiming an incomplete authority protocol. Current `net.gd` confirms the exact dangerous path the plan targets: `request_place()` reaches any-peer `_request_place()`, which calls validation-free `BuildSystem.place_remote()`, while remote remove reaches `destroy(true)`; the proposed sender, receiver, projection, and callsite guards match those seams.
- Canonical costs are verified in `recipe_db.gd`: hammer 3 wood/2 stone, campfire 2 wood/5 stone, workbench 10 wood, and six wood pieces at 2 wood each total 27 wood/7 stone. Current `player.gd` grants club/10 wood/6 stone/5 raspberries, so the nominal 17 wood/1 stone shortfall is correct.
- Persistence, interaction, settings, raid, and enemy seams are repository-grounded. `save_system.gd` currently mutates live state incrementally and writes directly; `main.gd`, `ui_root.gd`, and both dev scripts directly own interaction effects; `spawn_manager.gd::_process/_start_raid` owns raid spawning; `enemy.gd` emits `died`; Greyling is 20 HP.
- Representative remote rejection, one-slot migration, shelter gating, and interaction-controller tasks can be implemented after Phase 0 freezes the listed contracts. The two-process negative invariant is substantially stronger and clearer than pass 3.
- Representative starter and save/reload simulation remains contradictory. The plan says the starter grant is "persisted before inventory delivery" in the world transaction and reconciled after interruption, but the current world save contains the inventory itself. A crash after persisting a delivered marker but before inventory delivery/re-save makes reconciliation unable to distinguish “not delivered” from “delivered then legitimately spent”; re-granting can duplicate materials, while not re-granting can lose them. No transaction state machine, journal/snapshot representation, or recovery rule resolves that window.
- The first-session chain ends in "save/reload," but acceptance only says reload at every objective cursor is monotonic. It never defines the observable completion event/predicate for the final objective, whether the save must include its own completion, or how it avoids a save-after-load loop. Current load is callable in-world and Continue loads at startup, so executors and reviewers would have to choose semantics.
- The local atomic build contract names consume/create/revision/progress as one transaction, but current operations are in-memory mutations with no rollback mechanism; `Inventory.consume()` can only remove and `_spawn_piece()` can fail after consumption. The plan specifies failure invariants but not a commit/rollback ordering or preconstruction/reservation strategy. Phase 0's generic "prove atomic" gate does not give the executor a representative implementation path.
- Remote interaction scope is internally inconsistent. The exact surface says every mutating `BuildPiece.interact` branch gets an RT1 remote-client guard and acceptance claims a representative branch, but the repository has no network request path from `RemotePlayer` to `BuildPiece.interact`; only the local `Player` calls it. Conversely, the mutation matrix says craft/equip/eat are stably unsupported where invoked remotely while exact rejection surfaces and two-process tests do not define any such ingress. The plan must separate existing remotely reachable ingress from defense-in-depth local guards and avoid requiring invented command surfaces.

## Missing Evidence
- Definitely missing: crash-safe starter grant state transitions that make persisted grant state and inventory effects one recoverable invariant without duplication or loss after legitimate spending.
- Definitely missing: final save/reload objective semantics, including exact completion event/predicate, persistence ordering, and a finite restart/Continue scenario.
- Definitely missing: implementable local build transaction commit/rollback mechanics and failure injection points, including inventory capacity/representation and piece-construction/add-child failures.
- Possibly unclear: ownership persistence for the shelter predicate. The plan requires persisted owner IDs, but does not specify the additive piece field/default for legacy pieces or how owner identity is assigned and validated during local placement/load. This should be frozen with the piece schema.
- Possibly unclear: build validator reason order omits the current `_valid`/eligibility cases for no target/hit and invalid or empty recipe, and `UNKNOWN_PIECE` cannot describe all preview/confirm failures. Phase 0 should freeze a total result mapping for every `try_place()` return path.
- Thin scope/value evidence: 14–20 engineering days includes 2 days contract freeze + 5–7 + 5–7 implementation days, while the file estimates sum to 17.5–23.5 engineer-days before the separate 3 QA days. Reconcile the estimate and explicitly budget the new stores/controller/tests rather than retaining two incompatible totals.

## Approval Boundary
Phase 0 contract work, UI wireframes, repository mutation-ingress inventory, recipe fixtures, remote build fail-closed design, MAR1 deferral, raid guard design, and read-only authority projection design may proceed. Product implementation is not unblocked until starter recovery, final save/reload completion, local build atomicity, owner-field migration, and reachable remote-interaction scope are made explicit. No MAR1 capability is approved.

## Summary
- Clarity: Stronger and mostly explicit; critical starter/save/build transitions still require invention.
- Verifiability: Excellent negative-network and UI evidence; final objective and transaction interruption outcomes are incomplete.
- Completeness: Remote deferral is complete, but starter recovery and local atomic commit mechanics are not.
- Big Picture: The solo slice and fail-closed multiplayer boundary fit RT1; estimate accounting is inconsistent.
- Principle/Option Consistency: MAR1 deferral and no-false-success are consistent; starter pre-persist wording conflicts with exactly-once delivery.
- Alternatives Depth: Remote options are credible; starter transaction and local atomicity alternatives are absent.
- Risk/Verification Rigor: Broad and objective, but the highest local duplication window lacks an executable invariant.

## Required Changes
1. Specify a crash-recoverable starter grant protocol. Define durable states/data, the atomic relationship to inventory serialization, reconciliation after every interruption point, and behavior after materials are legitimately spent. Add tests for crash before marker, after marker/before inventory, after inventory/before commit, and after commit/reload; each must produce exactly one grant with no duplication or loss.
2. Define the terminal save/reload objective as a finite state machine. State which semantic save event records the pre-reload checkpoint, what load/Continue event proves reload, when completion is persisted, and how the next launch observes completion without requiring another reload. Add clean and legacy restart scenarios.
3. Give the local placement transaction an implementable commit strategy: validate all fallible conditions first, reserve/check inventory representation, construct/add the piece without authoritative publication, then commit consume + registration/revisions/evidence; or define compensating rollback for each failure. Freeze failure injections and assert no mutation for each.
4. Scope remote guards to actual ingresses. Inventory current network-reachable entrypoints; distinguish reject-only RPC sinks, client-local UI prevention, authority projection, and defense-in-depth methods. Do not add craft/eat/equip/interact RPCs merely to reject them. Define how tests invoke a representative interaction guard without fabricating product support.
5. Freeze the persisted piece ownership field, validation, and legacy default/inference policy used by the campfire shelter predicate, with save/load fixtures proving another/unknown owner cannot satisfy it.
6. Define a total typed placement result for every confirm path, including no placement surface, empty/invalid recipe data, inactive mode, and current geometry failures; align UI copy and precedence tests.
7. Reconcile the headline estimate with the file-owner subtotal and Phase totals, including whether Architect/Docs/Tools work overlaps or is additive.
