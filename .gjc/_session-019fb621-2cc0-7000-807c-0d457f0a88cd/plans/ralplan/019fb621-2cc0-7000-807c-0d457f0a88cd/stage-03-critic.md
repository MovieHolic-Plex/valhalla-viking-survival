## Claim Checks
- The cost baseline is repository-grounded: `scripts/core/recipe_db.gd` defines hammer 3 wood/2 stone, campfire 2 wood/5 stone, workbench 10 wood, and floor/wall/roof at 2 wood each, totaling 27 wood/7 stone. The plan incorrectly says the host derives build cost from `ItemDB`; canonical build costs currently live in `RecipeDB`.
- The starter baseline is verified in `scripts/player/player.gd`: club, 10 wood, 6 stone, and 5 raspberries. The planned authoritative, interruption-safe grant is a real cutover from unconditional `_ready()` inventory writes.
- The named load-bearing files exist: `game_state.gd`, `save_system.gd`, `net.gd`, `build_system.gd`, `build_piece.gd`, `inventory.gd`, `player.gd`, `ui_root.gd`, `main.gd`, `hud.gd`, `spawn_manager.gd`, `enemy.gd`, `loc.gd`, `net_probe.gd`, and `screenshot_director.gd`. The new stores/controller/registry/test adapters are explicitly new. Current code confirms the stated seams: direct inventory consumption precedes network placement, remote placement bypasses validation, save load mutates live state incrementally, raid mutation is in `spawn_manager.gd`, and mouse/pause/input-lock writers are spread across `main.gd`, `ui_root.gd`, and both dev scripts.
- Representative implementation simulation exposes unresolved contracts. Registration can bind an ENet peer, but the plan supplies no credential or challenge that authenticates a claimed durable `player_id`; knowledge of a UUID is not authentication. A disconnected player's ID can therefore be claimed by another peer despite repeated claims of authenticated reconnect identity.
- Replay simulation exposes a direct contradiction: validation checks current session epoch before replay lookup, so a request from a retained old-epoch ledger returns `STALE_SESSION`, while the immutable retry rule and the two-process “old-ledger replay” case imply retrieval of the original outcome. Retaining old ledgers is not enough unless the plan defines whether old-epoch retries replay or are always stale and aligns validation, acceptance, and tests.
- Capacity simulation exposes another contradiction: at 1,024 outcomes/4 MiB with all entries protected for 60 seconds, a new command must return final `REJECTED/RATE_LIMITED`, but there is no capacity to record that immutable outcome. Its retry therefore cannot be guaranteed to reproduce the same final acknowledgement.
- Identity migration is not yet implementable as specified. A legacy ID fingerprint includes “canonical slot identity + original seed + normalized original world name,” but the current save has one mutable path/name and no persisted original identity. Rename/move before first migration can alter that fingerprint. The plan also requires an in-app duplicate-world operation and multi-document collision scan, while the current product has one fixed `world1` slot and the file/UI scope assigns no world browser, duplicate command, or migration registry surface.
- The raid guard maps correctly to `_process()`/`_start_raid()` in `scripts/world/spawn_manager.gd`; `enemy.gd` provides the Greyling death event seam. The interaction cutover paths are also representative and actionable after its transition table is frozen.
- Settings coverage is incomplete at file level. SFX players are hard-routed to `Master` in `scripts/core/sfx.gd`, the wind ambient player is created in `main.gd`, sensitivity is consumed in `player.gd`, and project audio-bus configuration may require `project.godot` or a generated bus layout. These are not all assigned in the settings work or shared-file handoff, so executors would have to infer ownership and routing.

## Missing Evidence
- Definitely missing: a durable-player authentication/trust mechanism, including first registration, reconnect proof, credential storage/rotation/revocation, host-local behavior, and threat boundary. “Transport authenticates the RPC sender” authenticates only the connection peer, not ownership of a durable UUID.
- Definitely missing: one consistent old-epoch replay rule and a capacity-safe way to preserve immutable `RATE_LIMITED` outcomes.
- Definitely missing: a realizable source for immutable legacy “original” slot/name identity and a scoped owner/API/UI decision for duplicate, rename/move, delete, and multi-save discovery behavior.
- Definitely missing: settings/audio/reduced-shake callsite inventory and shared-file ownership for `sfx.gd`, ambient audio creation, `player.gd`, camera/FX shake sites, and any bus configuration artifact.
- Thin acceptance evidence: performance timing boundaries/sample counts/warm-up and capture method are undefined; “blinded coding and intervention rules” are referenced but not stated; “prepared Greyling survival 7–8/10” is ambiguous because 9–10 successes would apparently fail; semantic screenshot assertions are named but not enumerated per state. These prevent objective review from reproducing the gates.
- Thin persistence semantics: exact schema validation constraints, canonical JSON/byte-size accounting for the 4 MiB ledger limit, and failure behavior when onboarding-row deletion fails after world deletion remain deferred without acceptance-level outcomes.

## Approval Boundary
Phase 0 repository inventory, fixture authoring, wireframes, and contract investigation may proceed. Product implementation, authentication claims, replay/ledger implementation, legacy identity writers, duplicate-world UI/API, settings routing, and release-gate execution are not approved until the contradictions and missing contracts below are resolved. Raid guard and canonical cost fixture design may proceed, but build cost authority must reference `RecipeDB` (or an explicitly introduced canonical catalog), not the current `ItemDB`.

## Summary
- Clarity: Strong decomposition and cut line, but several normative contracts conflict.
- Verifiability: Broad suite design is good; performance, playtest, and visual semantics need operational definitions.
- Completeness: Missing durable-ID authentication, world-management scope, and concrete settings/audio ownership.
- Big Picture: Contract-first RT1 is coherent, but the identity/network substrate is larger than the current single-slot/unauthenticated architecture and must be explicitly bounded.
- Principle/Option Consistency: Authority and no-false-success principles are sound; old-epoch and rate-limit behavior violate immutable-outcome claims as written.
- Alternatives Depth: Main product alternatives are credible; authentication and legacy identity alternatives are absent.
- Risk/Verification Rigor: Risks are well recognized, but the highest-risk identity proof and ledger-full states lack executable resolutions.

## Required Changes
1. Define the durable-player authentication model. Specify credential material and storage, registration/challenge flow, reconnect proof, duplicate-live-binding behavior, rotation/revocation/recovery, host-local path, and explicit non-goals. If RT1 cannot authenticate durable identity, rename the guarantee and remove security claims rather than treating a claimed UUID as authenticated.
2. Resolve old-epoch semantics. Choose either: replay lookup of authenticated retained old-epoch request IDs returns the immutable original outcome before stale-session rejection; or every old-epoch packet is `STALE_SESSION` and old outcomes are snapshot/diagnostic-only. Update validation order, immutable-outcome wording, ledger retention purpose, acceptance, and the “old-ledger replay” test consistently.
3. Make full-ledger rejection recordable and deterministic. Reserve bounded rejection capacity, define a separate deterministic admission cache, or specify that capacity rejection is transport-level/non-final and exempt it from immutable replay. Add fixtures at both count and byte ceilings, including repeated retries while all entries are protected.
4. Correct canonical build-cost ownership from `ItemDB` to `RecipeDB`, or introduce one explicitly named immutable recipe catalog and assign the migration/callsites. Keep the 27 wood/7 stone fixture against that owner.
5. Redesign legacy identity derivation around data that exists and remains stable before first migration. Define canonical path/slot normalization, persisted migration-registry location, behavior for copied byte-identical legacy files, and whether pre-migration rename/move stability is possible. Scope and assign duplicate/rename/delete/multi-save discovery UI/API work, or remove the in-app operations and corresponding release claims from RT1.
6. Expand the file/callsite and ownership table for settings: `sfx.gd`, wind/ambient audio creation, audio bus artifact/runtime creation, `player.gd` sensitivity/invert application, and all reduced-shake camera/FX sites. Resolve shared ownership ordering for `main.gd` and `player.gd`.
7. Operationalize release evidence: define measured action start/end markers, warm-up, sample counts and trace source; enumerate screenshot semantic assertions per state; include the blinded coding/intervention rubric; and rewrite Greyling survival as an unambiguous threshold or justified target band.
8. Specify persistence edge outcomes and schema constraints, including onboarding cleanup failure after successful world deletion and exact ledger byte accounting, so interruption and sentinel fixtures have one expected result.
